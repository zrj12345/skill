# 软著材料生成

产出**三件套**：软著信息表、设计原理说明书、源代码文档。三者命名与口径必须一致
（软件全称、版本号、源程序量）。

**操作说明的默认落点是「嵌入设计原理说明书第二章各功能模块小节」，不是单独出一份
Word**——这是 CMS 软著最终过审的范式，务必照做：截图带**红色手写箭头标注**（数字圆
+箭头+楷体红字）与**敏感信息马赛克**，且截图必须**紧扣本软著主题**（只放与申请表
主要功能直接相关的界面，不要塞统计、系统管理等跑题页面）。
只有用户**明确**说「单独出一份操作说明书 / 用户手册」时才另立 Word。
按 `references/operation-manual.md` 写：以用户视角按模块写连贯操作步骤、每步配真实截图，
功能条数覆盖申请表全部主要功能。只写「每张图配 2~4 句说明」不够
（**CMS 软著就是这么被打回的，这条是踩坑经验**）。

被驳回要补真实界面截图、脱敏、手写标注时，走第 6.5~6.8 节，
详细流水线与检查清单见 `references/screenshot-supplement.md`。

## 0. 先做的事

1. **读模板**：用户通常给一个既往材料目录（如 `StreamEdge/`）作为格式基准。
   技能已附带三件套原件 `assets/templates/`（StreamEdge 的 `源代码.doc`、
   `设计原理.docx`、`软著信息表.doc`），可直接复制后改内容；用户另有模板时以用户给的为准。
   先解析模板，别凭记忆写。模板可能是两种格式：
   - 扩展名 `.doc` 但实为 docx 包（zip）→ 直接 `zipfile` 解 `word/document.xml`
   - 真 OLE2（`\xd0\xcf\x11\xe0` 文件头）→ 需 `olefile`
2. **读源码**，划清**本次申请的模块范围**。多版本分批申请时，一次只写一部分，
   把亮点留给后续版本（否则后续没素材可写）。

## 0.5 换项目复用（用本技能给别的项目写软著时先看）

技能分两层。**文中的账号、URL、数量、截图张数都是案例值，新项目一律按实际替换。**

**A. 通用、可直接用**（脚本均已支持 CLI 或环境变量）
- `shoot_pages.py`：`--base / --out / --token-file / --info-file / --pages`
- `desensitize.py`：新项目用 `--no-defaults --extra boxes.json`；
  内置规则只是 CMS 示例，不要把它当成通用脱敏规则
- `replace_media.py`：`--doc / --orig / --marked`，dry-run 默认
- `verify_delivery.py` / `pdf_patch.py` / `wps_export.py` / `strip_metadata.py`
- `assets/templates/` 三份模板原件可直接复制到新项目

**B. 示例实现，需按新项目改**（路径已可用环境变量覆盖，文案仍内嵌）
- `gen_info_table.py`：改 `T1 / T2 / NOTES` 的软件名、版本号、模块、技术特点、
  源程序量；`SC_BASE` 指定输出目录
- `gen_source_doc.py`：改 `SC_CODE_DIR`（源码根）、`V1_FILES`（取材文件清单）、
  `TARGET_PER_SIDE`（每侧页数）；`SC_BASE` 指定输出目录
- `gen_design_doc.py`：正文里的模块名/接口/流程必须按新项目重写；`SC_BASE` 指定根目录
- `figure_lib.py`：`SC_FIG_DIR` 指定出图目录，图内容按新项目画
- `page_count_sim.py`：`SC_ROOT` 指向新项目三件套目录，底部锚点必须换成
  **已知真实页数**的文档，否则校准无效
- `handmark_reference.py`：`SC_SRC / SC_DST` + `MARKS / SHORT`
  （CMS 的 22 张图配置只是示例，必须重写）

**C. 换项目的标准动作**
1. 复制 `assets/templates/` 到新项目，读模板与源码划分申请范围（一次只写一部分）
2. 填信息表文案 → 画竖版流程图 → 生成三件套 → 页数校验（锚点校准 + WPS 实测）
3. 用户要「系统操作说明 / 操作介绍」时，按 `references/operation-manual.md` 把操作说明
   **嵌入设计原理说明书第二章各功能模块小节**（默认，不单独成册）：覆盖申请表全部
   主要功能、每步配图、截图加红色箭头标注+马赛克、紧扣主题、不写真实账号密码
4. 被打回要补截图时走 6.5~6.8：登录截图 → 脱敏 → 手写标注 → md5 替换 → 校验
5. 交付前清属性、逐项目检截图、提醒用户关闭 WPS 后重新打开

## 1. 硬性指标（以实测模板为准）

| 材料 | 指标 |
|---|---|
| 源代码文档 | 前、后各连续 **30 页**共 60 页；每页 **≥50 行**；编程语言 ≤4 种 |
| 设计说明书 | 提交前 30 + 后 30 页；每页 ≥30 行 |
| 信息表 | 字段齐全，源程序量与代码范围口径一致 |
| **操作说明**（默认嵌入设计原理第二章） | 按模块写连贯操作步骤 + 真实界面截图（红色箭头标注 + 马赛克），覆盖申请表全部主要功能、紧扣主题；仅用户明确要求时才单独成 Word；正文不写真实凭据 |

⚠️ **关键**：页数不是按“段落条数”算，而是按**渲染后的折行行数**算。
按段落数取材会少页（实测某版 3060 段只出 57.6 页）。

### 项目不足 60 页时（小项目）

规则原文是「按前、尾各连续 30 页共 60 页提供（**不足 60 页提供全部代码**）」。
所以小项目**交付全部代码**即可，不要为了凑页数去放大字号
（字号变大会让每页行数跌破 50 行，反而违规）。
先算总账再决定取材方式：

```
渲染行数 ≈ 原始行数 × 1.03（Go 代码实测）
页数 = 渲染行数 ÷ 55.2（Consolas 11.5pt 版式）
```

实测两个案例：

| 项目 | 原始行数 | 渲染行数 | 页数 | 取材 |
|---|---|---|---|---|
| shortcms-freshflick（V1 范围） | 5542 | 5758 | 60 | 前 30 + 后 30 页，中间加省略标记 |
| search-proxy（全部 Go） | 1761 | 1819 | ≈33 | 全部代码，不截断 |

小于 60 页时**不要加省略标记**（没有省略）；交付时明确告知用户
“本项目代码不足 60 页，按规则提交全部代码”，并给出可选方案
（补充相关仓库 / 接受当前页数）。

### 页数仍不足时：纳入第三方依赖库源码

自有代码不足 60 页、或想要凑足 60 页时，可纳入项目**所依赖的开源组件**源码
（用户明确要求时这么做；MIT / Apache 等许可允许，文档中应标注组件名与许可）。
Go 项目可直接取本地模块缓存，无需联网：

```
go env GOMODCACHE                 # 例如 C:\Users\<user>\go\pkg\mod
<GOMODCACHE>\github.com\gin-gonic\gin@v1.10.0\   # 版本号对齐 go.mod
```

只取**非测试** `.go` 文件（`*_test.go`、`testdata/` 排除），并保持语言单一
（全部 Go，避开“编程语言 ≤4 种”的限制）。

**排版技巧——自有代码切成两段，保证完整收录**：
自有代码往往略多于 30 页（例如 33 页），若直接「自有代码 + 库代码」再取
前 30 + 后 30 页，会有约 3 页自有代码落进省略区间。做法是把它切成两段：

```
[自有代码 主体]                     ≈30 页  ← 前 30 页
// ……（中间部分源代码省略）……
// ------ 以下为第三方开源组件源代码：<组件>（<仓库>，MIT License）------
[库代码 尾部]                       ← 后 30 页
// ------ 以下为项目自身源代码（续）------
[自有代码 剩余文件]
```

要点：分段点选在**文件边界**，不要切到半个文件；三段注释（省略标记、
第三方来源标注、续接标注）让审阅者可读。实测：自有 1761 行（33 页）
+ gin 尾部 1500 行 → 60 页，自有代码一行不丢。

注意 `源程序量` 字段仍应填**自有代码**行数，不要把第三方库计入。



## 2. 设计说明书：照模板的标题结构写

模板（StreamEdge）的骨架——**照抄这个层级与叙事套路**：

```
[H1 22pt] 软件名称 + 设计说明书
[H2 16pt 黑体] 一、总体架构概述
     正文段 + “核心目标：” + ● 项目符号
[H2] 系统功能模块设计          -> 表(模块名称 | 功能说明)
[H2] 系统架构图                -> 图（图内无标题，靠本行带出）
[H2] 核心模块设计说明
    [H3 16pt] 模块名
        功能描述： + 正文 + ● 列表
        xx流程图： -> 图
        接口设计： -> 表(接口名称|请求方式|参数|返回示例)
        数据结构示例： -> JSON 段（仅首个模块）
[H2] 运行设计                  -> 表(项目 | 描述)
[H2] 附录：流程图汇总          -> 编号引导语 + 图 ×2
```

要点：
- **正文 10.5pt 两端对齐**，正文段首行缩进 2 字符（420 twips=21pt）
- **项目符号用真 ●**（模板用 Wingdings `\uf06c`），缩进 left 840tw / hanging 420tw
- **每个模块配一张流程图**，图内**不要写标题/图注**，由正文引导语带出
- 模板篇幅基准（StreamEdge 实测）：≈2100 字、8 图、6 表、**9 页**
  - 图占位是关键：模板 8 张图竖版约 12×14cm，合计占 ~108cm 版面
  - 横版图占位不足会让页数掉一半 → **流程图用自上而下竖版**

## 3. 图怎么画（PIL，竖版，可校验）

用 `scripts/figure_lib.py`：

- 画布 1000 宽、高 700–1210（竖版，显示宽 12cm 时约对应 8–14cm 高）
- 中列盒子宽 400 居中；菱形 320；右侧分支盒 250
- 字体：**微软雅黑** `msyh.ttc`（标题 `msyhbd.ttc`），**绝不要手写点阵字库**
- 2 倍超采样绘制后 `resize(LANCZOS)` 降采样，线条才不发虚
- 配色：中性墨色 `(38,42,48)` + 单一蓝强调 `(52,120,200)`，模块用浅色填充区分
- 连接线用正交折线 + 实心三角箭头（`vlink/hlink/elbow`）
- **必须做布局校验**：`Fig.validate()` 检查越界与节点重叠；
  `Fig.fit()` 自动缩字号防文字溢出。渲染后无法肉眼复核时这是唯一保障。

## 4. 页数校验：用可自校准的模拟器

`scripts/page_count_sim.py` 读 docx 真实排版参数（页面/页边距/字体/字号/行距/
图片高度/表格几何）模拟 Word 分页。

**必须先用已知页数的锚点校准**，再外推新文档：
```
锚点1：StreamEdge/设计原理.docx     真值 9 页，模型 10 页
锚点2：旧版源代码.docx（已实测）     真值 60 页，模型 66 页
→ 模型系统性高估 ~10%，按比例折算新文档
```
同时可用**粗粒度折行模型**交叉验证：
单行容量 = 文本宽度 / 字符宽；Consolas@11.5pt 每行 79 个半角单位
（CJK 按 1.819 折算），`ceil(units/79)` = 该行折行数。
版面行数 ≈ 3312 → 60 页（55.2 行/页，A4+上下1.5cm+左右1.6cm+Consolas 11.5pt+单倍行距）。

## 5. 信息表：照模板的两列表格

模板是**两列（6.44cm / 11.0cm）带边框表格**，不是“字段：值”的段落列表。
表一 17 行：软件全称 / 软件简称 / 版本号 / 软件分类（4选1）/ 开发完成日期 /
发表状态（2选1）/ 权利人名称 / 证件号码 / 开发的硬件环境 / 运行的硬件环境 /
开发该软件的操作系统 / 软件开发环境或开发工具 / 该软件的运行平台 /
软件运行支撑环境或支持软件 / 编程语言 / 源程序量 / 开发目的
表二 5 行：面向领域行业 / 软件主要功能（200字内）/ 软件特点标签 /
软件技术特点（100字内）/ ※注意事项※（合并单元格）
末尾另附 3 段“鉴别材料要求”。

字段标签**必须连括号里的填写说明一起保留**（如“软件分类（4选1）”）。

## 6. 环境坑（务必先看）

- **WPS 会锁文件**：用户开着文档时，`os.remove/rename/replace` 全失败
  （`PermissionError`）。做法：先写 `xxx(V1).docx`，提示用户关闭 WPS 后再改名；
  同目录 `~$xxx.docx` 是锁标志。
- **`Word.Application` COM 名可能被 WPS 接管**：此时 `win32com` 调 Word 会
  **无限挂起**（不是报错）。别反复重试、别设长超时死等。
  ✅ **实测可行解**：先试 `win32.Dispatch('Kwps.Application')`（WPS 自己的 COM 名），
  成功则用 `Documents.Open(..., ReadOnly=True)` + `SaveAs(pdf, FileFormat=17)` 转 PDF，
  `ComputeStatistics(2)` 读真实页数，最后 `doc.Close(False)` / `app.Quit()`。
  这条能拿到**真实页数 + 可渲染目检**，比模拟器更可靠；失败再退回第 4 节模拟器。
  仍要给命令设硬超时（如 150s），避免残留 WPS 进程。
- **PNG 扫描行必须自上而下**：手写 PNG 时 `for y in range(h)`，
  写成 `range(h-1,-1,-1)` 会整图上下翻转。
- **python-docx 中文字体**：`run.font.name` 只设 `w:ascii`，中文须补
  `w:eastAsia`；`rPr` 可能为 `None`，用 `get_or_add_rPr()`。
- **docx 内置换图片**：python-docx 无 API。直接改 OOXML zip：
  从 `word/_rels/document.xml.rels` 取 rId→`word/media/imageN.png`，
  按正文 `r:embed` 出现顺序覆写；**宽高比变了要同步改** `wp:extent` 与
  `a:ext`（每处 `<w:drawing>` 块内两处都要改），否则 Word 会拉伸变形。

## 6.5 审查补正：补真实界面截图到已有文档

被驳回意见常见为「请在文档鉴别材料中补充该软件运行**全部功能**所对应的界面截图，
并配合文字介绍软件相关操作；截图需真实、完整、清晰，功能操作介绍需连贯、全面，
体现出与申请表中填写的**主要功能、技术特点、源程序量**相符合」。

**用户常要求「放进第二章/第三章的对应章节，不要新建章节」** —— 这点必须严守：
只在已有小节末尾追加「引导段 + 图片 + 图注 + 操作说明段」，
不新增任何章/节标题，不改目录。

### 流程

1. **读申请表**：把「软件主要功能」「技术特点」「源程序量」原文抄下来，
   所有文字说明必须逐条呼应（如「四大模块」「统一鉴权」「RBAC 菜单与接口权限」
   「关联引用」「约 5500 行 Go 源程序」）。
2. **登录进系统**：Vue SPA 需真浏览器。`agent-browser` 的 daemon 在本机可能反复
   挂起（SIGTERM）→ 直接用 **Python Playwright + 系统 Chrome**：
   `pip install playwright`，然后
   `pw.chromium.launch(headless=True, executable_path=r'C:\Program Files\Google\Chrome\Application\chrome.exe')`
   （本机 ms-playwright 缓存版本常与新装 playwright 期望版本不符，指定系统 Chrome 可免下载）。
3. **绕过验证码**：从源码找初始化账号（`migration.go` 的 `userInit()`，如 s001/123456），
   `GET /api/v1/code` 拿 uuid + base64 验证码图片 → 用 ViewImage 目检读出 4 位码 →
   `POST /api/v1/signin` 拿 token。
   **不要**用 `/api/v1/info` 时带多余 header（会 502）。
4. **注入登录态**：前端多为 pinia-persistedstate，key = store id（本案 `user`）。
   `ctx.add_init_script("localStorage.setItem('user', JSON.stringify({token, userInfo}))")`。
   `userInfo` 必须带 `/info` 返回的 **menus**，否则左侧导航不渲染、截图看不出功能全貌。
5. **批量截图**：从前端 JS bundle 提取路由表（`path:"..."`）或 `/info` 的菜单树，
   逐页 1600×1000 截 `full_page=True`；再补关键操作子页（新增/编辑弹窗、权限树）。
6. **脱敏**：日志类页面可能显示登录请求的明文密码/验证码 —— 用页面自带
   **路径精确搜索**过滤出纯业务记录再截（模糊词常返回 No Data，要用完整路径）。
7. **插入文档**：`python-docx`，用 `anchor._p.addprevious(new_p._p)` 把新建段落
   插到「下一小节标题」之前。锚点用 `startswith` 且**取最后一次出现**
   （目录里也有章节名，取第一个会插错到目录里）。
   图片 `run.add_picture(path, width=Cm(15.5))`；正文首行缩进 21pt、宋体 10.5pt；
   图注居中加粗 9.5pt（与原文一致）。
8. **操作说明**：若用户要求操作说明或驳回意见强调「介绍软件相关操作」，
   默认把操作说明**嵌入设计原理说明书第二章各功能模块小节**（CMS 过审范式，结构见
   `references/operation-manual.md`），复用同一批「脱敏+手写标注」截图，按模块写连贯
   操作步骤，条数覆盖申请表全部主要功能、紧扣软著主题。仅用户明确要单独 Word 时才另出。
9. **校验**：章节标题序列前后完全一致（49→49）、表格数不变、图片关系无断链、
   图注全部落在目标章区间内、文档属性仍为空。
10. **目检**：`Kwps.Application` 转 PDF → PyMuPDF 渲染几页看图是否被拆页/裁切。

### 排版要点
- 图注编号用「图 2-1 … 图 2-22」按章编号，**不与原有图号体系冲突**即可
  （原文可能已有「图 3-2」「图 4-1」等乱序编号，别去改它）。
- 每组开头写一段**引导语**串起操作链路（登录 → 内容资产 → 编排 → 基础数据 →
  分发触达 → 权限审计），每张图配 2–4 句具体操作说明，做到「连贯、全面」。
- 截图宽 15.5cm（A4 可用宽 16.6cm），1600×1000 → 约 9.7cm 高，一页放得下两张。

### 6.6 截图上手写标注（补正材料的加强做法）

用户可能要求直接在界面截图里用画笔标出操作步骤。参考样式：**红色实心小圆写
白色数字 1 / 2 / 3 / 4 + 红色手绘短箭头指向控件 + 楷体红字短句写在步骤旁边**。
不要规整模板、不要 ①②③ 圈码字符、不要额外加白底说明带、不要统一对齐。

- Pillow 叠加透明标注层，**不扩展画布**，尺寸与原图一致 → docx 的
  `<wp:extent>` 不用改、页数不变
- 字体 `C:\Windows\Fonts\simkai.ttf`，34px @1600 宽（Word 15.5cm 宽时约 9pt 可读），
  `stroke_width=1` 红色描边加粗笔画 + 1px 白描边 + ±2° 倾斜；图上只写 6~10 字短句，
  完整连贯说明留在正文
- 落点自动选空白：8 方向随机 + 背景干净度评分（排除黑字与彩色控件，白留白和
  弹窗外灰遮罩都算干净）+ 重叠惩罚；顶部按钮区禁止向上（否则数字圆会跑到标题栏）；
  弹窗页优先写在四周灰遮罩；构图特殊的页面单独固定落点
- 控件坐标不必手工估：用**颜色块连通域检测**从截图自动提取
  （蓝 `#409EFF` / 红 `#F56C6C` 按钮）
- **替换图片用 md5 映射**：以「标注前备份.docx」的 media 为基准匹配原始 PNG，
  只换 ZIP 内对应 media 字节，其余 part 原样保留。基准固定，可重复执行、可回退。
  校验点：段落/表格数、正文文字、`extent`、图片数、图注区间、文档属性
- WPS 转 PDF 目检后**再清一次文档属性**（WPS 打开会写入作者 `admin`）
- 用户若嫌 `【按钮名】` 形式生硬，把图上短句改成自然说法（「点【搜索】」→「点搜索」）；
  正文若本来没有方括号就**不要动正文**

### 6.7 界面截图的敏感信息打马赛克

补正材料里的系统截图常带可识别信息，**过滤掉整条记录不如打码**（审查意见要求
「真实、完整、清晰」，删行会显得不完整）。必查五类：
① 顶栏右上角当前登录账号（几乎每张都有）；② 用户列表的登录账号与真实姓名；
③ 日志页的用户名列与客户端 IP；④ 登录页图形验证码明文；
⑤ **服务端地址 / URL / IP:端口 / 主机地址**。
弹窗页背景里仍可见的账号**同样要打码**。
⚠️ 自动扫描只覆盖表格列里的规则文字，URL 这类细笔画常漏网
（本案 `http://207.121.108.68:9927` 是用户复核时指出的）。
交付前必须**逐张图肉眼过一遍**，别只信脚本输出。

- 顺序必须是 **原图 → 马赛克 → 手写标注**：批注在最上层不被盖住，且落点评分
  会自动避开彩色马赛克块。不要直接在已标注的图上打码
- 马赛克实现：区域 `resize(w//9,h//9, BILINEAR)` 再 `resize(w,h, NEAREST)` 贴回，
  块大小 9px 左右最像常规脱敏
- **细笔画文字（URL/IP）用 `v' = 255-(255-v)*2.2` 放大对比**，否则像素化后是
  一片很淡的灰条、像涂抹而非马赛克；增强后才是与顶栏头像一致的灰白方格
- 表格文字位置用**深色像素行扫描**自动定位（列内逐行统计 `<150` 的像素数，
  连续行成段，段高 5~46px），比手工估坐标准；表头用 y 起点避开
- ⚠️ **弹窗遮罩会让整片背景变暗**，扫描会误判成「一整段文字」而失效 →
  这类页面改用固定行框（与同结构列表页行位一致），且框元组顺序统一为
  `(x0, y0, x1, y1)`，别写成 `(x0, x1, y0, y1)`
- 日志「内容」列是业务请求参数（video_id 等），非凭据/个人信息，**保留不打码**，
  以免大面积遮挡影响「完整清晰」
- 打码后仍走 6.6 的 md5 映射替换 + 属性清理 + WPS 转 PDF 目检流程

### 6.8 工具替代路径与本次新增的坑

- **PowerShell COM 可能被安全策略拦截**：`New-Object -ComObject Kwps.Application`
  直接报 "Command blocked for security"，别在此反复尝试。
- **pywin32 / comtypes 可能未安装**：`import win32com` 报 ModuleNotFoundError 时，
  不要将 WPS 导出当作必经步骤。用 PyMuPDF 直接替换已有 PDF 的内嵌图：
  `scripts/pdf_patch.py --pdf P --old OLD.png --new NEW.png`；
  用 `page.get_image_info(xrefs=True)` 确认页面引用的是新对象。
- **WPS 占用 docx**：`os.replace` / `shutil.move` 报 WinError 5，
  但 `open(path,'wb')` 覆写可行（见 `scripts/replace_media.py`）。
- **用户 WPS 窗口缓存**：直接覆写磁盘文件后，用户已打开的窗口仍显示旧内容；
  必须在交付说明里提醒「关闭后重新打开，不要在旧窗口保存」，
  否则用户一保存就把改动覆盖回去。
- **漏打码补做**：从 `_打码前_*` 备份出发重新生成，不要在已马赛克的图上二次打码；
  补做只动用户指出的那一处，其它已确认内容保持不变。
- **WPS 导出会写回作者 `admin`**：导出 PDF 后再跑一次 `strip_metadata.py`。

## 7. 收尾

- **清理文档属性**（必做）：python-docx 生成的 docx 会带
  `作者=python-docx`、`备注=generated by python-docx`，交付前必须清掉。
  用 `scripts/strip_metadata.py <目录…>`：
  移除 `dc:creator` / `dc:description` / `cp:lastModifiedBy` / `cp:contentType`
  及标题、主题、关键词、类别等自由文本字段；保留 `cp:revision` 与创建/修改时间。
  注意 `~$xxx.docx` 锁文件与 WPS 占用——被占用时脚本会报 SKIP，需用户关闭后再跑。
  清理后务必验证：zip CRC、`core.xml` 可解析、段落/表格/图片数不变、可正常打开。
- 若在设计原理第二章嵌入了操作说明：核对软件全称/版本/源程序量与信息表一致，
  功能模块数覆盖申请表全部主要功能，正文无真实账号密码/服务端 IP，
  截图已「脱敏+红色箭头标注」且紧扣本软著主题（无跑题页面）
- 临时脚本用完即删；产物留在项目目录
- 把模板规格、标定参数、踩坑写进项目 memory
- 交付时说明：各文档页数（及校验方式）、范围取舍、遗留问题（如锁文件）
- 若用户端 WPS 还开着文档，额外提醒「关闭后重新打开再复核」，
  避免旧窗口保存覆盖已替换的图片
