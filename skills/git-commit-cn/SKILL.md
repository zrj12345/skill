# Git Commit Cn

## Workflow

1. 检查提交范围。
- 先查看 `git status --short --branch`、`git diff --stat`、`git diff --name-status`。
- 默认只提交和当前需求直接相关的源码、资源、文档变更。
- 默认排除缓存、日志、编译产物、临时目录、下载文件、IDE 配置等明显无关内容；只有用户明确要求时才提交这些文件。
- 如果工作区存在大量无关未跟踪文件，不要直接使用 `git add .`。

2. 核对每个文件的真实改动。
- 逐个阅读待提交文件的 diff，必要时补看 `git diff -w`，区分功能改动和纯格式整理。
- 只写 diff 能证明的事实，不要臆测需求背景，不要把格式化写成功能点。
- 对二进制资源，按可验证信息描述，例如“更新登录背景图资源”“更新 GeoIP 城市库”。

3. 按固定格式撰写中文提交信息。
- 提交信息正文直接使用下面格式，不额外改成英文 Conventional Commit，也不要改成一句话摘要：

```text
- 修改 path/to/file
    - 修改点 1
    - 修改点 2

- 新增 path/to/file
    - 新增内容 1
    - 新增内容 2
```

- 文件块之间保留空行。
- 路径写相对仓库根目录的真实路径。
- 子项必须具体，优先写“新增字段/移除字段/修复某处逻辑/更新资源/调整限制”这类可审计描述，避免只写“优化”“调整”“处理一下”。
- 如果某个文件只有格式整理，就明确写“整理模板缩进”“统一属性顺序”“修正代码对齐”。

4. 执行提交。
- 只 stage 已确认纳入本次提交的文件，避免使用 `git add .`。
- 为了保留多行中文格式，优先把提交信息写入临时文件，再执行 `git commit -F <message-file>`。
- 提交完成后，反馈提交哈希。

5. 执行 `git push`。
- 当用户调用本 skill 时，默认继续执行 `git push`，不因为已经展示了提交信息而停下来等待确认。
- push 前先确认当前分支与上游分支关系，例如查看 `git status --short --branch` 或 `git rev-list --left-right --count HEAD...@{upstream}`。
- 如果当前分支在本次提交前已经领先远端，默认继续 push，并在结果中明确说明这次 push 同时推送了之前尚未推送的提交。
- 如果当前分支已经设置上游分支，优先执行 `git push`。
- 如果当前分支没有上游分支，使用 `git push -u origin <branch>`，并在结果中说明已建立上游跟踪关系。
- push 完成后，反馈分支名、远端名和推送结果；如果是无改动可推送的 no-op，也要明确说明。

## Guardrails

- 没有可提交的 diff 时，不要创建空提交。
- 遇到变更范围明显混杂、无法安全判断哪些文件属于本次需求时，先说明冲突点，再让用户确认范围。
- 不要重写用户没有要求改写的历史提交。
- 不要在提交信息里使用未经核实的测试结论；若未执行验证，就不要写“已验证通过”。
- 不要为了 push 擅自处理用户未要求的冲突、rebase、merge 或强推。
- 只有在下面这些情况才停下来等待用户确认，而不是默认直接 push：
  - 推送需要 `--force`、`--force-with-lease`、rebase、merge、解决冲突，或任何非快进处理。
  - 当前分支没有可用远端，且无法合理推断应该推送到哪里。
  - 本地已有未推送提交且明显可能与当前需求无关，继续 push 可能把不属于本次任务的历史提交一起发出去。

## Output

- 先给出拟使用的中文提交信息，但不要默认停下来等确认。
- 只要没有触发上面的需要确认场景，就继续完成 `git commit` 和 `git push`。
- 完成后反馈提交哈希、分支、远端、是否建立上游、以及是否连同历史未推送提交一起推送。
